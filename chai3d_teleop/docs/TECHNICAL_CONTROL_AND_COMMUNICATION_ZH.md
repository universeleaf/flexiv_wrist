# Flexiv 7/9DoF 遥操作控制与通信技术参考（中文在前 / English follows）

本文面向需要理解、调试和继续开发本项目的人。重点是控制逻辑、动力学、数据流、
实时通信、三个遥操作模式以及稳定性处理。UI 只是启动和改配置的入口，不是控制器
本身，因此这里只做简要说明。

> 重要边界：本文描述的是研究代码，不是经过医疗认证的控制器。模式 3 的接触力
> 必须先在刚性或可退让的非人体夹具上验证方向、大小、稳定性和急停行为。

## 1. 系统由哪些部分组成

硬件链路包含四部分：

1. Flexiv Rizon4s：原生 7 个关节，Flexiv RDK 提供状态、模型和 1 kHz 实时关节
   力矩接口。
2. 两轴外置腕部：Joint 8 由 moteus ID 2 驱动，Joint 9 由 moteus ID 1 驱动；
   通过 mjbots fdcanusb 和 CAN-FD 与电脑通信。
3. omega.7：提供三维平移、三维旋转、clutch 按钮以及三维力反馈。
4. 三踏板：只负责选择模式；真正开始和停止运动仍由 omega.7 clutch 决定。

软件按职责拆成三层：

- Python 协调层：默认入口直接调用 Flexiv NRT Cartesian 接口；同时读取手柄、
  踏板和腕部，完成坐标映射、9DoF 几何分配、Mode 3 力轴管理和触觉反馈。
- C++ 实时控制层：用于 `demo7`、`demo9` 和显式的实验入口 `teleop-osc`；每 1 ms
  更新模型并运行自定义 7DoF/9DoF torque OSC。它不是默认 `teleop` 的执行路径。
- 驱动内环：Flexiv 执行实时关节力矩；moteus 默认以自己的高速位置环跟踪 C++
  求出的 q8/q9 目标，并叠加平滑后的重力/接触力前馈。

主要文件如下：

| 文件 | 作用 |
|---|---|
| `run.py` | 简短命令入口 |
| `scripts/teleoperate.py` | 默认三模式入口：Flexiv NRT Cartesian + 腕部协调 |
| `scripts/teleoperate_rt.py` | 实验性全 torque-OSC 的目标协调与共享内存 |
| `controllers/cpp/flexiv_9dof_torque_osc.cpp` | 三模式的 1 kHz 实时控制核心 |
| `controllers/cpp/rt_osc_common.hpp` | OSC、轨迹、矩阵和力矩整形公共函数 |
| `controllers/nine_dof.py` | 无硬件依赖的几何、模式状态机和辅助控制逻辑 |
| `controllers/teleop.py` | 手柄相对映射与稳定触觉反馈 |
| `controllers/wrist_dynamics.py` | 腕部质量、惯量、重力、科氏和摩擦参考模型 |
| `hardware/wrist_moteus_bridge.py` | moteus 状态和命令子进程 |
| `hardware/rt_teleop_bridge.py` | Python/C++ 遥操作共享内存协议 |
| `config/nine_dof_teleop.toml` | 实际运行配置，也是 UI 保存的配置 |

## 2. 进程、线程和更新频率

> 当前默认 `python3 run.py teleop` 是完整三模式入口：Mode 1/2 使用 Flexiv RDK
> 自带的 `NRT_CARTESIAN_MOTION_FORCE` 笛卡尔阻抗；Mode 3 在同一个机器人会话内
> 使用柔和的混合操作空间位置/姿态/Tool-Z 力控制，腕部使用 OSC 外环和 moteus
> 位置内环。`python3 run.py teleop-osc` 仅保留为三个模式全部使用自定义 1 kHz
> `RT_JOINT_TORQUE` 的研究对照。下面明确标为“C++ 力矩 OSC”的结构只适用于后者。

系统不是所有设备都运行在同一个频率，因此必须明确谁负责快速稳定、谁只提供较慢
目标。

| 路径 | 典型频率 | 责任 |
|---|---:|---|
| Flexiv C++ RT 调度器 | 1000 Hz | OSC、质量矩阵、重力、关节力矩输出 |
| Flexiv 状态/模型 | 1000 Hz | q1..q7、速度、法兰位姿、Jacobian、M、C、外力 |
| omega.7 CHAI3D 桥 | 1000 Hz | 手柄状态和触觉输出 |
| 默认 Python 遥操作协调循环 | 100 Hz | RDK Cartesian 目标、手柄、踏板和腕部协调 |
| 默认 fdcanusb/moteus 腕部桥 | 100 Hz 目标值 | 顺序服务 q8/q9；实际到达频率受 USB/CAN 事务时间影响 |
| 实验 C++ torque-OSC 的腕部桥 | 50 Hz | 给 1 kHz C++ 发布带时间戳的 q8/q9 状态 |
| moteus 内部伺服环 | 驱动器内部高速 | q8/q9 的稳定位置跟踪 |

C++ torque-OSC 才会在每个 1 kHz 周期读取“最新一帧”腕部状态；默认 NRT 路径没有
这个 1 kHz C++ 环。两条路径都不会假装 USB 链路也是 1 kHz。
腕部速度先低通，再进入阻尼和动力学；腕部位置仍使用实时测量值。这个多速率结构是
稳定性的关键。

## 3. 启动顺序和控制权交接

运行默认的 `python3 run.py teleop` 后，正常顺序如下：

1. 读取并验证 TOML 配置。
2. 启动 omega.7 桥，确认位置、旋转和按钮状态有效。
3. 启动腕部桥，按配置处理 Joint 8/9 零位与状态。
4. 检查 Flexiv 当前 active Tool、质量、CoM、惯量和 TCP 是否与配置一致。
5. Flexiv 切换到 `NRT_CARTESIAN_MOTION_FORCE`，读取机器人提供的 `K_x_nom`。
6. 程序按 `[teleop_impedance]` 缩放六轴刚度，调用 RDK 的
   `SetCartesianImpedance`；阻尼比也直接交给 Flexiv。
7. 程序把当前七轴姿态设为零空间参考，并启用参考姿态跟踪，避免冗余解漂移。
8. 系统保持当前 TCP，等待踏板选择 Mode 1、Mode 2 或 Mode 3。
9. 模式选好后必须松开再按下 clutch；按下瞬间同时捕获相对位姿零点和当前七轴
   零空间姿态。

`python3 run.py teleop-osc` 的启动过程才会建立共享内存、检查实时权限并切换到
`RT_JOINT_TORQUE`。两个后端都在 Ctrl-C 时清零触觉输出、STOP 腕部并停止 Flexiv。

Ctrl-C 的停止顺序是：清零触觉力、请求腕部 STOP、停止 Flexiv 实时流、切回安全
停止状态并关闭共享内存。通信持续丢失、驱动 fault 或机器人 fault 仍会停止系统；
这些是故障边界，不是会话运动范围限制。

## 4. 坐标系与手柄映射

omega.7 的平移和旋转是相对控制：按下 clutch 的瞬间，记录手柄姿态和探针姿态。
之后使用“手柄相对变化”生成“机器人相对目标”，因此手柄不需要与机器人处于相同
绝对坐标。

当前关键配置：

```toml
[haptic]
translation_scale = 1.0
axis_map = "-x,-y,z"
rotation_axis_map = "-x,-y,z"
rotation_command_sign = [-1.0, -1.0, 1.0]
```

当前实机配置另外为 Mode 1 单独反转 XZ 平面旋转（绕手柄局部 Y 轴）：

```toml
rotation_command_sign = [-1.0, -1.0, 1.0]       # Mode 2
mode1_rotation_command_sign = [-1.0, 1.0, 1.0] # Mode 1
```

该改动只影响 Mode 1 的 XZ 旋转方向，不改变平移，也不改变 Mode 2 中 Joint 8
已经确认的方向。

`translation_scale = 1.0` 表示手柄移动 20 mm，机器人目标移动 20 mm，即平移
1:1。旋转也是自然 1:1。这个比例不限制总工作空间，只改变输入灵敏度。

代码实际读取 omega.7 的三轴位置、完整 3×3 姿态矩阵和 clutch 开关。clutch 只
决定何时捕获相对零点，不把 gripper 开合角当成连续运动命令。按下瞬间记录手柄
姿态 `Rh0` 和探针姿态 `Rp0`，随后使用手柄自身坐标中的相对旋转：

```text
ΔRh_local = Rh0ᵀ Rh
ΔRp_local = axis/sign mapping(ΔRh_local)
Rp_target = Rp0 ΔRp_local
```

旧实现使用 `Rh Rh0ᵀ` 并把增量左乘到探针上。这是设备基座坐标的旋转；只要按下
clutch 时手柄有倾斜，前后、左右和 yaw 就会串轴。现在的局部坐标公式保证正、负
输入在任意起始姿态下都产生相反目标。运行日志中的 `haptic_local_rot_deg` 是映射
前的手柄局部旋转，`target_local_rot_deg` 是映射后的探针局部目标，可逐级判断方向。

平移和旋转使用独立映射，不能因为调整平移方向而意外改变 Joint 8/9 的旋转方向。
坐标符号的最终判断应始终通过低速、无接触测试完成。

输入侧还有两个稳定性处理：

- deadband：忽略编码器噪声和非常小的无意移动。
- Python 在 100 Hz 采用 GitHub 版单周期速度边界；C++ 在 1 kHz 继续做连续的
  速度/加速度整形。前者抑制输入跳帧，后者避免力矩台阶。

手柄到达物理边缘时，松开 clutch，把手柄移回舒适位置，再按下 clutch。重新按下
瞬间以“当前实测 TCP + 当前手柄姿态”建立新 anchor，旧的未完成目标不会被继承。
因此可以反复 clutch、无限累计工作空间移动，同时每次重新接合都没有位姿跳变。

## 5. clutch 和踏板状态机

三个踏板只做“模式锁存”：

- Pedal 1：Mode 1，默认是 Flexiv 内置 7DoF 笛卡尔阻抗。
- Pedal 2：Mode 2，Flexiv 内置阻抗 + 腕部优先的 9DoF 几何分配。
- Pedal 3：Mode 3，在同一个默认入口中启用固定点、仅姿态输入、腕部优先和 Tool-Z
  恒力的柔和混合 OSC。力轴有接触门控，不会在空气中自动搜索表面。

如果踩踏板时 clutch 正按着，新模式不会立即运动。必须先松开 clutch，再重新按下，
这样新模式会从当前实测姿态重新捕获 anchor，避免使用上一个模式的旧零点造成跳变。

clutch 的含义非常明确：

- 按下：当前模式开始接收手柄目标。
- 松开：立即停止更新遥操作目标，捕获释放时的实测关节角，进入保持。
- 松开后手动推机器人：机器人可以被外力暂时偏离。
- 外力消失：机器人回到松开瞬间捕获的位置，而不是追赶松开前的滤波目标。

## 6. 阻抗后端与 OSC 后端的区别

当前默认 Mode 1/2 不称为自定义力矩 OSC。它直接使用 Flexiv RDK 的笛卡尔阻抗控制器：

1. Python 生成目标 TCP 位姿并调用 `SendCartesianMotionForce`。
2. Flexiv 内部负责轨迹生成、笛卡尔弹簧/阻尼、机器人动力学、重力补偿和七轴
   执行。
3. Python 不计算也不发送 Flexiv 七轴力矩。
4. clutch 按下时刷新 `SetNullSpacePosture`，所以同一个 TCP 的冗余解倾向留在当前
   姿态，不会自行寻找远处关节解。

配置中的 `stiffness_scale` 是对机器人自己报告的 `K_x_nom` 逐轴缩放；它不是另造
一套质量模型。`damping_ratio=0.70` 直接传给 Flexiv。

Mode 3 仍在同一个 `NRT_CARTESIAN_MOTION_FORCE` 会话中，但任务从自由空间阻抗切换
为混合操作空间控制：X/Y 和姿态属于运动/阻抗轴，探针 Tool-Z 在检测到真实接触后
成为主动恒力轴。它不是另一个进程，也不会让两个控制器同时争夺 Flexiv。

clutch 按下和松开使用两套刚度：

```toml
stiffness_scale = [0.25, 0.25, 0.25, 0.35, 0.35, 0.35]
released_stiffness_scale = [0.04, 0.04, 0.04, 0.08, 0.08, 0.08]
released_nullspace_reference_tracking = 0.10
```

松开时捕获当前 TCP 作为弹簧平衡点，然后把平移刚度降到标准值的 4%、旋转降到
8%，零空间姿态阻力也降到 0.10。用手推时可以明显偏离；外力撤去后，因为平衡点
没有被更新，机器人会返回松开瞬间的位置。这是柔顺位置保持，不是 freedrive。

`teleop-osc` 才是下面描述的自定义七轴操作空间力矩控制。它仍被完整保留用于比较，
但默认工作流的 Mode 3 已经不需要切换入口。

OSC 是 Operational Space Control，即操作空间控制。直观理解是：控制器先考虑
“探针应该到哪里、朝向哪里”，然后利用实时 Jacobian 和质量矩阵，把这个末端任务
换算成每个关节需要的力矩。

普通关节 PD 只看到每个关节的角度误差；OSC 看到的是探针在三维空间中的位置和
姿态误差。它还能利用多余自由度：只要探针任务不变，内部关节可以选择更自然的
姿态。

实时控制器每 1 ms 做以下工作：

1. 读取 q1..q9 和速度。
2. 用当前 q8/q9 计算探针相对法兰的实时位置和姿态。
3. 计算完整探针 Jacobian。
4. 更新 Flexiv 七轴质量矩阵，并加入外置腕部的动态惯量耦合，得到 9×9 矩阵。
5. 计算末端位置/姿态误差和速度误差。
6. 用 OSC 生成任务力矩，再加零空间、科氏、动态重力和腕部物理前馈。
7. 经过执行器额定力矩与力矩变化率边界后发送。

这里的“力矩边界”是电机硬件额定能力和防止命令突变的必要边界，不是人为限制
工作空间，也不会因为检测到 15 N 接触力就退出任务。

## 7. Mode 1：7DoF 遥操作

Mode 1 只让 Flexiv 原生七轴参与探针任务。默认入口中：

- 使用完整的三维位置 + 三维姿态目标。
- Joint 8 回应用层零位；Joint 9 保持 STOP/read-only，不参与任务分配。
- 手柄平移控制探针平移；手柄旋转控制探针姿态。
- Flexiv 自己的笛卡尔阻抗和内部动力学负责七轴控制。

只有显式 `teleop-osc` 研究入口才使用探针 Jacobian 的前七列 `6×7` 计算七轴
关节力矩 OSC。

因为只有七个关节解决六维任务，冗余度只有 1。与 9DoF 相比，Flexiv 大关节可能
需要更明显地改变姿态，才能完成同样的探针姿态目标。

这个冗余自由度不能在手柄静止时自行寻找旧姿态。每次按下/松开 clutch 或切换模式，
C++ 都同时锁存当前 TCP、当前七轴角和 q8/q9：任务误差为零，零空间姿态误差也为
零。因此 Mode 1/2 的手柄增量为零时，控制器只抵消速度、外扰和模型误差，不会把
机械臂拉向程序启动时或上一个模式的关节姿态。接合后只有在远离奇异点时，冗余参考
才以约 10 秒时间常数跟随操作者已经造成的运动；接近奇异点时冻结本次接合中最后的
健康参考，并由奇异值速度缩放降低继续靠近的速度。

按下 clutch 不再把 OSC 支撑力矩从 0 缓慢增加。因为当前 TCP 和关节姿态已经在同一
边沿锁存，OSC 可立即提供完整位置/姿态刚度；输出端的力矩变化率边界仍保证连续。
旧的一秒接入斜坡会先结束关节保持、再慢慢恢复笛卡尔支撑，因此 Elements 重力模型
只要有小量残差，Mode 1/2 就会在手柄未动时先下坠。进程启动和通信恢复的独立 ramp
仍然保留。

默认 Mode 1 运行在 Flexiv 的 `NRT_CARTESIAN_MOTION_FORCE`，并通过
`SetCartesianImpedance` 使用厂商笛卡尔阻抗；`teleop-osc` 入口仍可运行原来的
C++ 1 kHz `RT_JOINT_TORQUE` 版本。

默认 NRT 遥操作使用 `[robot]` 的 RDK Cartesian 目标边界：

```toml
max_linear_velocity_m_s = 0.5
max_linear_acceleration_m_s2 = 2.0
max_angular_velocity_rad_s = 1.0
max_angular_acceleration_rad_s2 = 5.0
```

这些是传给 `SendCartesianMotionForce` 的上界；实际动作还受 100 Hz 相对目标步长、
手柄速度和 Flexiv 内部轨迹生成限制。`teleop_osc.arm_*_kp/kd` 只属于显式
`teleop-osc`，不能把它们当成默认 Flexiv 内置阻抗的绝对刚度。

## 8. Mode 2：9DoF 遥操作

默认阻抗后端的 Mode 2 使用“腕部目标优先、Flexiv 补剩余量”的分配：

- q8/q9 的两轴 IK 先以 1:1 比例求解腕部真正能覆盖的姿态分量。
- 姿态分配使用未经过腕部速度整形的 IK 几何目标判断“这一部分最终能否由 q8/q9
  完成”。Flexiv 不会因为物理腕部正在平滑追赶而临时接管该旋转，再在稍后退回。
- Mode 2 的位置目标仍然是实际探针 TCP 尖端，不是腕部轴交点。Joint 8/9 转动时，
  Flexiv 只做保持该点所需的小量平移，抵消“转轴到 TCP”偏心距离形成的圆弧。
- 如果某个姿态分量完全可由 Joint 8/9 实现，原始 IK 分配会使 Flexiv 法兰姿态目标
  保持不变，因此七轴不会旋转；它只平移补偿 TCP 几何偏移。
- 手柄平移仍以 1:1 移动实际 TCP 目标点。
- Flexiv 七轴由厂商阻抗和厂商动力学控制；moteus 用内部位置环跟踪腕部目标。
- 手柄目标与 Mode 1 相同，没有人为放大腕部角度。
- clutch 按下时把当前七轴姿态发送给 `SetNullSpacePosture`，并令 reference
  tracking 为 1.0。它不冻结 TCP 任务，只抑制对任务没有帮助的整臂重构。

如果用 `python3 run.py teleop-osc`，Mode 2 则继续使用原来的位置优先分层 OSC、
实时 9×9 质量矩阵和动态腕部模型；两种实现并存，便于实机比较。

这个选择同时满足“TCP 位置准确”和“尽量少动七轴”：腕部负责可达姿态，七轴只做
腕部无法完成的姿态残差与维持 TCP 所必需的小量平移。物理上无法同时让偏心 TCP
固定、Joint 8 转动且七轴完全不平移，但不需要七轴旋转。

`wrist_priority_gain = 1.0` 的含义是“可达的腕部旋转分量只使用一次”。不再使用
2 倍等人为放大，因为放大会让 Flexiv 被迫反向补偿，容易产生看起来很大的内部
运动和抖动。

Mode 2 对法兰目标的姿态和平移使用不同的腕部状态：

- 法兰姿态由原始腕部 IK 目标计算，因此 Joint 8 可达的旋转从一开始就属于 Joint 8；
- 法兰平移由实时实测 q8/q9 计算，因此 Joint 8 尚未到位时，七轴仍能准确抵消当前
  偏心 TCP 的圆弧，保持 TCP 点不动；
- 结果是腕部较慢时探针姿态暂时落后，但七轴不会先旋转代做、再反向回来。

腕部位置命令还有一个 `15°` 移动跟随窗口：目标最多领先当前实测角 15°。这不是
总角度或工作空间限制；只要电机继续移动，窗口会一起移动，Joint 8 仍可走完整
`-90°..+90°`。若机构、线缆或负载使电机停止，命令不会继续累积到 25° 以上并让
整个遥操作退出。真实 moteus fault、通信中断和实测越过物理软件行程仍会 STOP。

日志中的 moteus `mode=11` 表示驱动命令 watchdog 超时，正常位置模式是
`mode=10`。双电机通过同一个 fdcanusb 顺序通信，一次事务偶尔可能超过 100 ms。
因此现在分成两个 watchdog：

- 上游 Python→腕部桥仍为 100 ms；协调器停止更新时，桥仍会迅速 STOP；
- moteus 驱动内部 watchdog 为 1000 ms，长于一次双电机串行事务，避免正常 USB
  抖动把电机切到 `mode=11`；
- 如果仍短暂出现 mode 11，桥会持续重发位置命令恢复 mode 10，并输出
  `WRIST_POSITION_MODE_RECOVERY`，而不是让目标误差无限增加。

默认腕部执行模式为 `hybrid_position_ff`：

1. C++ 用两轴腕部 IK 根据 1:1 手柄姿态算出 q8/q9 目标。
2. q8/q9 目标经过二阶平滑器，限制目标速度和加速度突变。
3. moteus 内部位置环快速、稳定地跟踪该目标。
4. C++ 只给腕部叠加平滑后的重力和模式 3 接触力前馈。

这样做仍是 9DoF OSC：腕部目标和 Flexiv 残差任务来自同一个末端目标，只是外部 USB/CAN-FD 链路
不适合直接承担 1 kHz 纯力矩内环。过去同时发送 C++ 任务 PD 和 moteus 位置 PD，
等于叠加两套刚度，是 9DoF 抖动的重要来源；当前结构只保留一套快速腕部刚度。

当前腕部目标直接读取经过 100 Hz 输入边界的最新姿态，Flexiv 七轴的剩余姿态目标
单独整形。默认 q8/q9 目标上限为 30/40 deg/s、120/160 deg/s²；Flexiv 剩余姿态
目标上限为 0.20 rad/s、0.60 rad/s²，增益为 18/8。这里没有放大角度：最终仍然是
1:1，只是先让腕部到达自然 IK 解，七轴以较慢的第二优先级补偿腕部不能表达的旋转
残差，并完成 TCP 平移。

左右反向时，平滑器会检查“保存的目标速度”是否与最新误差方向相反。如果相反，
先把该旧速度清零，再向新方向加速。旧实现没有这一步，所以快速从左转改成右转时，
整形器仍会保留一段向左角速度，看起来像左右输入都让机械臂向左。正负离线测试已
确认手柄映射和腕部 IK 本身会产生相反符号，问题位于旧目标速度的滞留，而不是轴
映射把两个方向变成了同一方向。

## 9. Mode 3：固定点、只控姿态、保持 Tool-Z 力

Mode 3 的用户输入规则：

- 手柄平移完全无效。
- 手柄旋转改变探针姿态。
- clutch 按下时的探针 TCP XYZ 被保存为固定接触点。
- Joint 8/9 优先、以 1:1 自然角度求解姿态；Flexiv 只补偿 TCP 固定点和腕部无法
  表达的小量姿态残差。
- Tool-Z 接触力目标由配置给出，当前保存的低力验证值是 `-5 N`。

固定点首先在 Python 目标层强制执行：目标 XYZ 永远等于 clutch 按下瞬间捕获的探针
位置，手柄平移数据根本不会进入 Mode 3 的机器人目标。只有手柄相对旋转被保留。

### 9.1 默认统一入口的固定点姿态控制

默认入口避免了“腕部还没跟上，七轴先做完整旋转，随后又退回”的动作：

1. 腕部 IK 先求 q8/q9 能自然完成的两个姿态分量，不做角度放大。
2. 未经速度整形的 IK 结果只用于判定最终应由腕部承担的姿态；因此 Flexiv 不会因为
   腕部暂时滞后就替它旋转。
3. 腕部实际命令仍经过速度、加速度和实测角附近的移动跟随窗口，再交给 moteus。
4. Flexiv 法兰只接收腕部无法产生的第三个姿态分量，并依据实测 q8/q9 做小量平移，
   抵消转轴到探针 TCP 的偏心圆弧。

Joint 8 的转轴不穿过探针尖端，所以“探针尖端固定且 Joint 8 转动”必然要求 Flexiv
做少量平移；这是几何补偿，不是手柄平移泄漏。若旋转完全属于腕部可达方向，Flexiv
不需要跟着旋转。

Mode 3 的 Flexiv 阻抗参数为：

```toml
mode3_stiffness_scale = [0.35, 0.35, 0.35, 0.20, 0.20, 0.20]
mode3_damping_ratio = [0.80, 0.80, 0.80, 0.80, 0.80, 0.80]
```

位置比普通自由空间遥操作稍硬，姿态较柔和，阻尼比取 RDK 允许范围上限 0.8，用于
降低换向反弹。Flexiv 内部完成七轴动力学和重力补偿；Python 不直接向七轴发送力矩。

腕部使用“OSC 外环 + 稳定位置内环”：OSC 根据探针姿态误差、腕部速度、腕部重力
模型计算 q8/q9 目标和前馈力矩；moteus 内部位置环快速跟踪 q8/q9 目标，前馈力矩只
负责减轻重力和动态负担。这里不再使用在当前固件上实测输出过小、会导致腕部看起来
不动的纯 NaN-position 前馈力矩命令。

### 9.2 默认统一入口的 Tool-Z 力控制

Flexiv 返回世界坐标系下的补偿外力，Python 用实时探针旋转把它投影到当前 Tool-Z。
力控制只在检测到正确方向且至少 2 N 的已有接触后锁存。在空气中，六个轴全部保持
位置控制，力命令为零，不会自动搜索表面。

接触锁存后，Flexiv 只把探针 Z 设为主动恒力轴，X/Y 与三个姿态轴仍由阻抗位置任务
保持。Z 轴最大速度设为 RDK 允许的最低值 `0.005 m/s`。目标力不从轻接触一步跳到
配置目标，而是从锁存时的实测力在 3 秒内线性缓升。若同方向接触低于 1 N
持续 50 ms，程序关闭 Z 力轴并退回固定点位置保持；脚本继续运行，重新建立 2 N
接触后可再次锁存。

由于恒力轴必须允许极小的法向位移，数学上不可能在同一 Z 方向同时要求“绝对零
位移”和“精确非零力”。这里的含义是：X/Y 固定，姿态围绕捕获点变化，Z 只允许
维持真实接触所必需的柔顺位移，且速度被限制为 5 mm/s。

### 9.3 实验性 `teleop-osc` 的差别

显式运行 `python3 run.py teleop-osc` 时，Mode 3 才使用 C++ 1 kHz 七轴
`RT_JOINT_TORQUE` 分层 OSC：XYZ 为主任务，剩余姿态投影到位置零空间，力项再通过
Jacobian 转为关节力矩。该路径保留用于研究比较，不是默认三模式工作流所必需。

### 9.4 “位置绝对固定”和“非零力”的物理关系

同一个自由方向不能同时独立保证数学上的绝对零位移和非零接触力：

- 在自由空间没有物体提供反力，要求任何非零接触力都必然会推动探针移动。
- 在刚性接触面上，表面提供反力；固定点阻抗只需产生非常小的弹性误差，就能与
  非零力任务达到平衡。
- 因此正确操作是先让探针在目标点稳定接触，再选择 Mode 3、松开、重新按下 clutch。

当前实现不会沿 Tool-Z 主动“搜索接触面”。如果需要自动搜索，应作为独立的接近
状态机实现，不能混入固定点姿态任务。默认混合控制在真实接触存在时调节到目标力；
没有接触时退回捕获点，不会为了凑够 15 N 在空气中移动机械臂。

## 10. 松开 clutch 后的硬保持

旧保持器使用所有关节共享的固定 Kp/Kd 力矩。Flexiv 各关节惯量差异很大，所以同一
Kp/Kd 会造成轻关节回得快并反弹、重关节回得慢，释放后还可能抖动。

当前保持器按以下方式工作：

1. 松开瞬间记录七轴实测角度作为 `q_release`。
2. 目标速度立即清零，不继续追踪手柄滤波器残留速度。
3. 用位置误差和关节速度生成一个过阻尼的“期望回位加速度”。
4. 用 Flexiv 当前质量矩阵把这个加速度转换成各关节力矩。
5. 加上 Flexiv 科氏项和实时腕部重力变化。
6. 经过原有执行器额定力矩与 slew 边界后发送。

配置如下：

```toml
clutch_hold_natural_frequency_hz = 1.0
clutch_hold_damping_ratio = 1.25
```

自然频率主要决定回位“硬度/速度”；阻尼比决定是否反弹。`1.0` 表示约 1 Hz 的
闭环自然速度，`1.25` 大于 1，是过阻尼。控制器没有积分项，所以人工持续推住机械臂
时不会无限积累积分；松手后仍会回到释放点。

调参原则：

- 回位仍太慢：每次把自然频率增加 0.1 Hz，观察峰值力矩和噪声。
- 接近目标时来回弹：提高阻尼比，例如 1.25 → 1.35。
- 感觉太硬或触碰不安全：降低自然频率。
- 不要为了“更硬”只把频率大幅提高；实际输出仍受电机额定力矩限制，过高只会更早
  饱和。

## 11. 质量矩阵、惯量矩阵和为什么它们是动态的

项目中有三种容易混淆的矩阵：

1. 6×6 空间惯量：描述一个刚体对三维平移和三维旋转的惯性。Flexiv Elements 中
   的 Tool 质量、CoM 和 3×3 转动惯量可以组成这个矩阵。
2. 9×9 关节质量矩阵：描述九个关节一起加速时需要多少力矩，并包含 Flexiv 与
   外置腕部之间的耦合。
3. 6×6 操作空间惯量：控制器从 9×9 质量矩阵和 6×9 Jacobian 实时换算，描述当前
   姿态下探针沿六个任务方向运动时的“感觉重量”。

腕部旋转后，两个腕部刚体的 CoM 位置、转动方向和 Jacobian 都变化，因此 9×9
矩阵和操作空间 6×6 矩阵必须每周期更新。代码不会把一次标定得到的单个矩阵直接
永久使用；标定得到的是质量、CoM、惯量、摩擦等物理参数，实时矩阵由这些参数和
当前 q8/q9 计算。

`inertia_mode = "auto"` 使用完整耦合模型。`legacy-block` 只用于诊断对比，它忽略
Flexiv/腕部耦合，不应作为真实 9DoF 默认运行方式。

### 11.1 为什么当前不让九个关节同时做一次辨识

当前采用分层辨识、联合建模：Flexiv 七轴的质量、CoM 和惯量由 Elements/RDK
提供；`identify-inertia` 只运动并辨识 RDK 不知道的 Joint 8/9。默认运动为 120 秒，
Joint 8 ±45°、Joint 9 ±60°。控制器运行时根据七轴姿态和 q8/q9，把两部分实时
组装为完整耦合的 9×9 关节质量矩阵，再得到 6×6 操作空间惯量。

真正的九轴联合参数辨识必须同步记录九轴的位置、速度、加速度和实际关节力矩。
Flexiv 数据环是 1 kHz 硬实时，而当前 moteus 腕部经过 Python、USB 和 CAN-FD，
只有约 50--100 Hz，且时延并不完全固定。直接把这两路数据放进同一个最小二乘
问题，会把时间错位和 USB 延迟拟合成虚假的质量或惯量，通常反而让 9DoF 控制更抖。
在腕部改为与 Flexiv 共时钟的硬实时接口前，不采用这种表面上“一次完成”、实际
精度更差的方法。

## 12. 重力补偿如何分工

Flexiv 和外置腕部不能简单地各自补偿完整总载荷，否则会重复补偿。

当前分工是：

1. Flexiv 内部重力补偿保持开启。Elements 中的 active Tool 被视为 q8=q9=0 时的
   基础刚体载荷。
2. C++ 根据当前法兰姿态和 q8/q9，计算两个移动腕部刚体对九个广义关节的完整重力
   影响。
3. 对 Flexiv 七轴，只发送“当前腕部姿态重力 − 腕部零位重力”。零位部分 Elements
   已经补过，这样不会重复。
4. 对 Joint 8/9，发送完整实时腕部重力，因为 Flexiv 内部模型不知道这两个外置
   关节。

发送给 Flexiv 的概念结构是：

```text
OSC任务力矩 + Flexiv科氏力矩 + 腕部姿态变化造成的七轴重力增量
```

调用 `StreamJointTorque(..., true, true)`，所以 Flexiv 自己的基础重力补偿和软限位
仍开启。我们不是完全接管 Flexiv 的基础重力模型，而是在它上面补动态腕部差值。

由于 q8/q9 只以约 50 Hz 经 USB 更新，直接把每个编码器台阶送入 1 kHz 力矩环会
形成力矩台阶。本次增加 `dynamic_gravity_filter_hz = 5.0`，只平滑模型重力前馈，
不修改实测位置，也不在任务控制中制造额外延迟。

## 13. 科氏、摩擦和腕部前馈

Flexiv RDK 模型提供七轴科氏/离心项。腕部模型根据 q8/q9、速度和辨识参数计算：

- 腕部重力；
- 腕部科氏项；
- 粘性摩擦；
- 经过平滑符号函数的库仑摩擦；
- 辨识出的力矩 bias。

在默认 `hybrid_position_ff` 中，moteus 的位置内环负责快速 PD，C++ 不会再次把
完整任务 PD 当作前馈发送，从而避免重复刚度。发送给腕部的主要前馈是低频物理项：
重力，以及 Mode 3 需要时的接触力分量。

## 14. 目标平滑与速度前馈

Python 从连续两帧目标位姿估算目标线速度和角速度，并低通后写入共享内存；当前
默认前馈增益为 0，因此只保留估算和接口，不把非实时差分速度注入力矩控制。C++
内部二阶目标整形器负责生成连续速度，并限制线/角加速度和速度。

这两者用途不同：

- Python 速度前馈告诉 OSC“目标正在移动”，减少跟随滞后。
- C++ 二阶整形防止非实时目标采样产生力矩台阶。

需要降低稳定性风险时，保持 `target_velocity_feedforward_gain = 0`，让 C++ 从目标
轨迹自身产生一致速度；只有经过真实日志确认 Python 时间戳和采样足够稳定后，才应
小幅增加该增益。

## 15. 触觉力反馈与防抖

Flexiv 世界坐标外力先减 bias，再变换到 omega.7 坐标。普通接触反馈默认是实测力
的 0.25 倍；超过阈值时增加渐进反作用和速度阻尼。omega.7 的 12 N 是输出饱和，
不是遥操作退出条件。

稳定触觉反馈包含：

- 外力低通；
- 小力 deadband；
- 力变化率限制；
- clutch 接入 ramp；
- 本地速度阻尼；
- 无源性观察器和能量罐。

当前实时 OSC 版本保留了 GitHub `main` 的遥操作外围语义：手柄采样、clutch
相对映射、手柄速度估计、反馈滤波和目标发布统一运行在 Flexiv 配置的 100 Hz
协调节拍。moteus 的 fdcanusb 通信仍独立保持 50 Hz，因此不会为了提高触觉刷新率
而把腕部串口负载翻倍。C++ 仍在 1 kHz 执行三种模式的 torque OSC，动态腕部重力
补偿也没有回退。

力反馈是否接通只由“已选择模式并按住 clutch”决定。它不再二次等待 C++ 的
`rt_enabled` 回执；该回执存在一个或多个跨进程采样周期的延迟，旧的二次门控会
令反馈短暂归零、重复触发接入 ramp，操作者会感到反馈忽有忽无或有冲击。Flexiv
RT 状态过期仍由独立 watchdog 处理，所以删除二次门控不会让失效状态继续输出旧力。

当前反馈信号仍取自 C++ OSC 发布的 Flexiv 补偿后世界坐标外力。启动时记录三轴
bias，运行时先减 bias，再做坐标映射、比例、过载反作用及下面的稳定化处理。这样
恢复的是 GitHub 版触觉行为，而不是把机械臂控制退回旧 NRT 模式。

能量罐的直观作用是：如果延迟后的反馈力正在持续向操作者/设备“主动注入能量”，
控制器只削减速度方向上的主动分量；正常静态接触力仍尽可能保留。这是解决“开力
反馈就抖、关力反馈就稳定”的关键机制。

本项目没有使用 Kalman filter。原因不是 Kalman 无效，而是当前主要问题是多速率
延迟、重复刚度、目标速度缺失和反馈能量注入，不是一个已知噪声模型下的状态估计
问题。简单低通、速度前馈和无源性控制更透明，参数更容易通过实测验证。未来如果
获得准确的传感器噪声与过程模型，可在不改变控制架构的前提下评估 Kalman 估计器。

## 16. moteus PID 与项目控制增益的区别

moteus 永久 `servo.pid_position.kp/ki/kd` 是驱动器内部输出轴位置环；本项目配置中的
`position_kp_scale` 和 `position_kd_scale` 是每条命令的临时缩放，不会写入驱动器
永久配置。

C++ 的 `translation_kp/kd`、`rotation_kp/kd` 是探针任务空间增益；
`wrist_tracking_kp/kd` 是纯力矩诊断路径的腕部目标跟踪增益；clutch hold 的自然频率
和阻尼比是释放状态的七轴保持参数。它们分别处于不同控制层，不能直接互换。

当前稳定默认策略是：

- moteus 内部位置环只出现一次，负责腕部快速稳定。
- C++ 计算 q8/q9 目标和物理前馈，不再叠加第二套快速腕部 PD。
- Flexiv 七轴始终使用 1 kHz C++ torque OSC。

## 17. Python/C++ 共享内存协议

共享内存用于同一台电脑上的低延迟通信，不经过 TCP。每个数据块包含 magic、序号、
时间戳和固定长度数组。

写入采用奇偶序号：

1. 写线程先把序号设为奇数，表示“正在写”。
2. 写入整帧目标或状态。
3. 最后把序号设为偶数。
4. 读线程只接受前后两次读到相同偶数序号的帧。

这样 C++ 不会读到“位置来自新帧、姿态来自旧帧”的混合数据。

遥操作命令包含：模式、enabled、目标位姿、目标线速度、目标角速度、Mode 3 Tool-Z
力目标和时间戳。C++ 状态包含：探针位姿、外力、q8/q9、当前模式、命令是否新鲜、
位置误差、姿态误差、Flexiv 剩余三轴姿态误差、奇异值、臂速缩放和力误差。

## 18. fdcanusb 与腕部 watchdog

USB/CAN-FD 不是硬实时链路，偶尔会出现 Linux 调度或 USB 帧延迟。控制器区分：

- 短暂 stale：Flexiv 进入当前关节保持，腕部命令 0 Nm，等待通信恢复。
- 持续 stale：超过 hard timeout 后停止，避免在未知腕部状态下继续输出。
- 恢复：重置腕部目标整形器并平滑重新接入，避免恢复帧造成跳变。

`command_timeout_s` 是单次 moteus 事务等待时间；`rt_osc_state_timeout_ms` 是状态
新鲜度；`rt_osc_hard_timeout_ms` 是连续故障停止时间。它们处理不同层级的问题。

不要同时运行两个访问同一 `/dev/ttyACM*` 的程序。出现“device disconnected or
multiple access”时，应先停止所有旧 bridge/tool 进程，再检查 by-id 链接和 dialout
权限。

## 20. 标定依赖

以下变化后必须重新检查 Elements Tool：探针、传感器、支架、线缆固定方式、腕部结构
或任何会改变质量/CoM/TCP 的零件。

Elements Tool 负责 Flexiv 看到的基础载荷和 TCP。项目的腕部惯量辨识负责外置两轴
相对运动造成的动态变化。两者不能互相替代：

- TCP 错误会直接让固定点和旋转中心错误。
- Tool 质量/CoM 错误会让 Flexiv 基础重力补偿错误。
- 腕部辨识错误会让 q8/q9 运动时的动态补偿错误。
- 电机零位错误会让几何、重力方向和 Jacobian 都错误。

只读检查：

```bash
python3 run.py check-tool
python3 run.py check-inertia
```

## 21. 日志如何判断问题来源

实时 CSV 默认在 `/tmp/flexiv_9dof_osc_rt.csv`，包含：

- 位置/姿态误差；
- Flexiv 和腕部速度范数；
- 七轴和腕部命令力矩；
- q8/q9 实测与目标；
- moteus 实际力矩；
- 9×9 质量矩阵和任务惯量条件数；
- 动态重力七轴增量范数；
- Joint 8/9 重力前馈。

常见判断：

- q8/q9 目标在动、实测不动：检查 moteus 模式、PID、扭矩能力和 CAN 状态。
- 目标与实测一起跳：检查 IK 分支、目标整形、零位和角度连续性。
- 只开触觉反馈才抖：检查外力 bias、反馈符号、延迟、无源性和本地阻尼。
- 松开后抖：检查实测关节速度噪声、保持频率/阻尼和动态重力列。
- Mode 3 点移动：检查是否在接触面、TCP 是否正确、模式 3 XYZ 误差以及力方向。
  `fixed_point_recovery=1` 表示控制器正在暂停腕部/本体的新姿态推进和力项，优先把
  TCP 返回 clutch 捕获点；恢复至 1 mm 内后会自动继续。
- Flexiv 动很多而腕部动很少：检查 q8/q9 目标、腕部位置内环和当前姿态是否接近
  腕部奇异方向。
- 左右方向不确定：比较 `haptic_local_rot_deg` 和 `target_local_rot_deg`。若前者
  正负对称但后者不对称，问题在映射；若两者对称而 `arm_residual_rot_deg` 长期
  单向，问题在腕部 IK/残差分配。
- `singularity_sigma` 下降且 `arm_speed_scale<1`：Flexiv 正接近几何奇异区，控制器
  连续减速但不会退出；松开 clutch，回到更安全姿态后重新捕获目标。

## 23. 本次修改摘要

本项目的主要稳定性和三模式改动包括：

1. 手柄平移设置为 1:1（`translation_scale = 1.0`）；旋转保持自然 1:1。
2. clutch 松开后的固定关节 Kp/Kd 改为实时质量矩阵整形的 1 Hz、1.25 过阻尼
   保持，使回位更硬、更一致并减少反弹。
3. 动态腕部重力增加 5 Hz 前馈低通，抑制 50 Hz 腕部编码器状态在 1 kHz Flexiv
   力矩环中形成台阶。
4. Mode 3 从“切向位置 + 释放 Z”改为“完整 XYZ 捕获点 + 只接收姿态 + 配置的
   Tool-Z 接触力”，并在 Python/C++ 两层锁定 clutch 捕获的接触点。
5. Python 目标速度前馈默认关闭，由 1 kHz C++ 目标整形器产生连续速度，消除掉帧
   导致的瞬时大速度命令。
6. 目标使用速度/加速度连续整形，Python 掉帧不会变成一步大跳。删除原 15 mm/8°
   硬误差窗口，因为它会把可用任务力压得过低而让机器人在有负载时卡住。短暂指令
   延迟只临时保持，数据恢复后自动从实测姿态继续，不再永久锁存等待重新按 clutch。
7. Mode 2/3 改为 1:1 腕部优先分层分配：q8/q9 先完成可达姿态，Flexiv 只补平移
   与姿态残差，不使用腕部运动放大。
8. Mode 3 加入 2 N 接触门控；未接触时恒力输出为零，避免非零力控制器在空气中
   主动寻找表面。Flexiv 残差采用低增益连续控制，不设会让运动突然停止的角度截断。
   此后又加入 14–16 N 宽容带、1 N/50 ms 接触释放迟滞和 1–3 mm 平滑位置优先门控：
   力项不再把 TCP 推离捕获点，接触消失或位置误差增大都只撤力、不退出任务。
9. Mode 3 的本体控制由单个 6D 加权 OSC 改为严格“XYZ 主任务 → 姿态零空间任务”；
   1–3 mm 恢复区同步暂停 q8/q9 与本体姿态推进，并把本体残余姿态目标整形限制在
   0.20 rad/s、0.60 rad/s²，使探针脱离时优先、自动返回固定点。
10. 恢复 GitHub 版 100 Hz clutch 映射及其单周期速度边界（0.5 m/s、1.0 rad/s
   换算到每周期），同时保留 C++ 的连续加速度整形。触觉与目标发布为 100 Hz，
   腕部 fdcanusb 仍为 50 Hz。
11. 触觉反馈恢复 GitHub 版 clutch 门控，不再由延迟的 `rt_enabled` 二次开关；
    状态日志新增无源限制标志和能量罐能量；动态腕部重力补偿保持不变。
12. 遥操作的 Flexiv 目标降为 0.12 m/s、0.35 rad/s，并使用独立的低增益阻抗；
    q8/q9 改为直接跟随最新 1:1 姿态目标，目标带宽提高到 4 Hz。平移、姿态和腕部
    整形器在检测到目标反向时会清除旧方向速度，修复快速右转后仍继续向左的问题。
13. 相对姿态从设备基座坐标 `R R0ᵀ` 改为手柄局部坐标 `R0ᵀ R`，并在探针侧
    后乘局部增量，修复非零起始姿态下左右/前后串轴和单向旋转。
14. Mode 2/3 把腕部原始目标和 Flexiv 剩余法兰目标分开整形：Joint 8/9 先自然
    跟随可达旋转，Flexiv 只平滑跟随不可达残差，不再为了抵消腕部延迟而突然转动。
15. 加入单位归一化 Jacobian 的几何奇异值监控。接近奇异区只连续降低 Flexiv
    目标速度并增加既有 OSC 正则化，不停止会话；q8/q9 仍保持自然 1:1 响应。
    冗余姿态参考只在健康区慢速更新，接近奇异区冻结最后的健康参考，避免每次
    reclutch 都把已经恶化的七轴姿态重新认作正常姿态。
16. 默认 `teleop` 合并三种模式：Mode 1/2 继续使用 Flexiv 厂商阻抗，Mode 3 在同一
    进程和同一机器人会话内切换为柔和混合操作空间控制，不再要求停止后另开入口。
17. 默认 Mode 3 的腕部从实测运动过小的纯前馈力矩改为“OSC q8/q9 目标和动力学
    前馈 + moteus 位置内环”，同时使用原始腕部 IK 分配 Flexiv 剩余姿态，防止七轴
    在腕部追赶期间替它大幅旋转。
18. 默认 Mode 3 增加 2 N 接触门控、3 秒目标力缓升、5 mm/s Z 轴速度和 50 ms
    接触释放迟滞；接触消失只退回捕获点位置保持，不退出完整遥操作工作流。
19. UI 增加独立的结构化遥测通道和 14 张实时图：一张全宽 Mode 3 力图、真实/规划
    TCP 位置、真实/规划 TCP 姿态、位置误差、姿态误差，以及九个关节的独立误差。
    遥测与普通日志分离，不执行 IK，不改变控制循环频率。

这些修改都保留了 Flexiv 自身基础重力补偿、软限位、驱动 fault、通信 watchdog、
执行器额定力矩和 Ctrl-C 停止行为。

## 24. UI 实时遥测与 14 张跟踪图

### 24.1 数据从哪里来

控制循环每次都已经拥有真实探针位姿、任务目标位姿、Flexiv 七轴状态和腕部两轴
状态。Python 只按 `[runtime].ui_telemetry_rate_hz`（默认 20 Hz）把这些现成数值序列化
成一条 `TELEMETRY` JSON；它不额外调用 Flexiv、moteus、IK 或动力学求解器。因此画图
不会阻塞 100 Hz 协调循环，也不会改变 1 kHz Flexiv 内部/实时控制节拍。UI 后端把
遥测和 Live Log 分开缓存，浏览器通过 `/api/status` 增量读取，避免重复传输全部历史。

### 24.2 Mode 3 全宽力图

力图显示实时 Tool-Z 测量、控制器低通估计、目标 sensed force 和接触门控/缓升后的
实际命令。它只画 Mode 3 样本。测量来自 Flexiv 外力投影，不是独立 Bota 地面真值；
四个信号的严格定义见第 29.3 节。

### 24.3 四张末端任务图

- **TCP Position — Actual vs Planned**：真实探针 TCP 和当前任务目标的世界坐标
  X/Y/Z，统一显示为 mm。
- **TCP Orientation — Actual vs Planned**：两者的绝对世界姿态都转换成旋转向量
  RX/RY/RZ，单位 deg。绝对旋转向量在接近 180° 表示边界时可能换符号，因此判断
  控制质量应优先看下一张“姿态误差”图。
- **TCP Position Error**：`target - actual` 的 X/Y/Z 和欧氏模长，单位 mm。
- **TCP Orientation Error**：由 `R_target * R_actual^T` 得到最短旋转误差，再显示
  RX/RY/RZ 和总误差角，单位 deg。这张图不会把三个欧拉角直接相减，所以能正确
  表达三维姿态误差。

位置误差和姿态误差是最直接的任务空间控制质量指标，在 UI 中使用重点边框。它们
来自完整腕部几何后的物理探针 TCP，而不是 Flexiv 法兰中心。

### 24.4 九张关节误差图

每个关节单独一张图，纵轴为 `q_target - q_actual`（deg），这样某一轴的跟踪问题不会
被其他八轴的量程压扁。J8/J9 的目标就是发给 moteus 位置内环的腕部目标，因而是直接
跟踪误差。

Mode 1/2 默认采用 Flexiv 的 NRT Cartesian impedance。该厂商接口公开实测七轴状态，
但不公开其内部每周期逆解出的关节目标。因此 J1--J7 使用本项目通过
`SetNullSpacePosture()` 发送的零空间参考作为 `q_target`。这九张图可用于观察姿态参考
偏离、腕部跟踪和冗余漂移，但不能把 J1--J7 曲线解释为厂商内部伺服误差。TCP 的四张
图没有这个语义限制，是判断实际遥操作精度的首要依据。

### 24.5 显示与缓存

浏览器只保留最近约 60 秒的样本，可切换 15/30/60 秒视窗。每张图独立自动缩放；误差
图以零为中心做对称缩放，便于看出正负偏差。点击 **Clear Plots** 只清除浏览器历史，
不会清除控制器状态、改变目标或停止任务。新任务启动时也会自动清空旧任务曲线，
避免把两个不同零点或模式的数据画在一起。

## 25. 答辩级系统定义：必须先分清两条控制路径

项目保留两条控制路径，因为它们解决的问题不同。教授问“你们现在用什么控制器”时，
不能只回答“OSC”，必须先说明运行了哪个入口。

### 25.1 默认真实遥操作路径

命令是 `python3 run.py teleop`，配置是
`runtime.teleop_controller = "flexiv_impedance"`。Flexiv 切换到
`NRT_CARTESIAN_MOTION_FORCE`：

- Mode 1/2 的七轴本体完全使用 Flexiv RDK 内置 Cartesian impedance；Python 给
  末端平衡位姿、刚度比例、阻尼比和零空间参考，不直接计算七轴力矩。
- Mode 3 仍在同一 RDK 模式中；X/Y 和姿态由 Cartesian impedance 控制，探针 Z
  可在接触门控后切换为 Flexiv 的 force-controlled axis。
- 外置 q8/q9 由 Python 做几何分配。Mode 2 用 moteus 位置内环；Mode 3 用腕部
  任务空间力矩外环计算姿态目标和重力前馈，再由 moteus 位置内环稳定跟踪。
- 该路径的好处是 Flexiv 自己处理七轴逆解、关节伺服、重力和厂商安全机制；缺点是
  RDK 不公开内部逐周期关节目标，也不能让我们修改厂商内部的动力学补偿细节。

### 25.2 自定义实时 torque-OSC 路径

`demo7`、`demo9` 和显式命令 `python3 run.py teleop-osc` 才会切换到
`RT_JOINT_TORQUE`。C++ Scheduler 以 1 ms 周期运行，读取 RDK Model 的 M、C、J，
自行计算七轴力矩。9DoF 版本把 Flexiv 七轴模型和辨识后的两轴腕部模型组合起来。
这条路径研究价值高、内部变量可见，但对实时权限、模型准确度、USB 时延、目标连续性
和奇异点更敏感，所以当前不作为默认遥操作后端。

## 26. 从手柄到探针的完整数据链

一次正常的 clutch 动作包含以下步骤：

1. 松开 clutch 时不累积手柄位移。Flexiv 保持最后捕获的平衡点，腕部保持当前角度。
2. 按下瞬间记录 omega.7 的位置/姿态、物理探针 TCP 位姿、七轴关节姿态、q8/q9、
   Flexiv 法兰姿态。所有后续命令都相对此快照计算，因此手柄达到机械边界后可松开、
   回到舒适位置、再按下继续，不改变机器人目标的连续性。
3. 平移先做 0.4 mm 径向死区，再乘 `translation_scale=1.0`，再通过
   `axis_map=-x,-y,z` 变换到机器人方向。
4. 旋转使用手柄局部相对姿态 `R_handle_anchor^T R_handle_now`，不是世界相对姿态。
   这样在任意倾斜角按下 clutch，局部前后、左右和扭转仍保持相同意义。
5. 旋转轴通过右手变换 `rotation_axis_map=-x,-y,z`，再乘配置的三个方向符号。
   Mode 1 有独立符号，因为它不把局部 Y 旋转分给 Joint 8；Mode 2/3 使用共同标定。
6. 目标使用相对增量后乘到按下时的探针姿态。用四元数/旋转矩阵组合，而不是直接
   相加欧拉角，所以不会因为欧拉角顺序产生固有串轴。
7. 0.25° 旋转死区只去掉设备抖动，且在边界连续减去死区，不会产生一步角度跳变。

配置中的轴映射必须是行列式 +1 的正交矩阵。单独写一个反射矩阵会破坏右手坐标；
需要反转某个旋转感觉时，使用 `rotation_command_sign`，不要破坏坐标基。

## 27. 默认 Mode 1：Flexiv 七轴 Cartesian impedance

Mode 1 的任务是让 Flexiv 七轴完成探针六维位姿跟踪，同时不主动使用 Joint 9：

- 选择模式后，`zero_hold_mask=[true,false]` 让 Joint 8 回应用层零位；Joint 9 保持
  STOP/read-only。这样演示的是七轴本体，而不是隐藏地借用第九轴。
- clutch 按下时，将当前 Flexiv 七轴 `q` 写入 `SetNullSpacePosture`。零空间目标不是
  任务空间目标；它只在多个关节解都能实现同一 TCP 时偏好当前姿态。
- `K_x_nom` 来自连接中的 Flexiv 机器人型号。本项目不猜绝对刚度，而用
  `[0.25,0.25,0.25,0.35,0.35,0.35]` 缩放厂商标称六轴刚度。平移较软以方便遥操作，
  旋转略硬以减少安装长工具时的姿态漂移。
- 阻尼比六轴均为 0.7，接近常用的充分阻尼但不过度迟缓设置。RDK 接收的是阻尼比，
  不是本项目直接填写的 N·s/m 数值。
- clutch 松开时，目标立刻捕获为当前实测 TCP，刚度降为
  `[0.04,0.04,0.04,0.08,0.08,0.08] * K_x_nom`，零空间参考跟踪降为 0.1。
  因此可用手推开；外力撤销后，虚拟弹簧返回松开时的平衡点。这个行为是阻抗控制，
  不是 admittance：输入仍是位置平衡点/刚度，机器人内部由外力造成位移。
- 每个 100 Hz 协调周期调用 `SendCartesianMotionForce` 更新目标；真正快速关节控制由
  Flexiv 内部执行，Python 的 100 Hz 不是电机电流环频率。

如果按下 clutch 后本体立即下坠，首先检查 active Tool 的质量/CoM/惯量，而不是先加
Cartesian Kp。错误重力前馈是持续偏置；加大刚度只能用更大的位置误差抵消它。

## 28. 默认 Mode 2：腕部优先的 9DoF 分层分配

九个关节不能简单同时对同一个姿态误差做高增益控制，否则 q8/q9 还没来得及通过
USB 运动，七轴本体已经把相同误差全部补完；随后腕部到达又迫使本体反向补偿，表现
为不必要的大幅往返和抖动。当前分配是分层的：

1. 先把目标探针旋转相对 clutch 锚点转换到 Flexiv 法兰坐标。
2. 用两轴腕部角速度 Jacobian 做阻尼最小二乘 IK。`damping=0.03` 在可观方向接近
   普通最小二乘，在两轴接近退化时抑制过大的角度步长。
3. 每次迭代最多 4°，最多 30 次，并预留 2° 关节边界。得到 q8/q9 能自然实现的
   两个旋转分量；`wrist_priority_gain=1.0`，所以没有人为放大腕部角度。
4. 两轴无法同时产生的第三个旋转分量留给 Flexiv。Flexiv 仍以 Cartesian impedance
   跟踪完整物理探针目标，但法兰目标已经除去腕部可达旋转，因此本体只补残差。
5. 原始腕部 IK 目标经过 1.5 Hz 临界阻尼二阶整形；速度为 q8 30°/s、q9 40°/s，
   加速度为 120/160°/s²。选这些值是为了低于当前减速器/负载下已经验证的跟踪能力，
   同时让动作明显可见。
6. 目标最多领先实测角 15°。这是随关节移动的跟随窗口，不是总角度范围；它防止
   卡住的电机积累几十度目标后突然释放。
7. moteus 使用永久 PID 的临时缩放 `kp_scale=0.2, kd_scale=1.0`。对应当前永久值：
   q8 的有效 P 约 200、D 约 30；q9 的有效 P 约 240、D 约 20。Ki 保留在固件内，
   但本项目不会每次启动重新写永久 PID。

保持探针位置时使用“解耦法兰目标”：腕部的原始 IK 角决定要从法兰姿态中扣除什么，
腕部实测角决定当前偏置尖端产生了多少位置弧。这样慢腕部不会让本体暂时代做腕部
旋转，但本体会做必要的小平移，补偿探针离腕部旋转交点的距离。

## 29. 默认 Mode 3：固定接触点、姿态输入和 Tool-Z 力

Mode 3 接收手柄旋转，不接收任何手柄平移。`orientation_only_target()` 每周期把目标
XYZ 强制改为 clutch 按下时的探针位置。q8/q9 仍先解决可达姿态，本体补偏置尖端的
平移和剩余旋转。

### 29.1 腕部姿态控制

腕部外环计算三维最短姿态误差和实际角速度，然后生成任务空间力矩，再用腕部角速度
Jacobian 的转置映射到两个关节。直观形式是“姿态弹簧 + 速度阻尼 + 重力前馈”。当前
外环刚度 6 N·m/rad、阻尼 0.35 N·m·s/rad；最后按 q8/q9 连续额定输出 6/2 N·m
饱和。由于实机 moteus 的纯 NaN-position 前馈力矩曾出现实际输出很小，稳定默认不是
纯力矩：C++/Python 外环算 q8/q9 目标和模型前馈，moteus 高速位置环跟踪目标并叠加
前馈。这避免再叠一套快速腕部 PD，也能克服减速器静摩擦。

### 29.2 Flexiv 混合位置/力控制

Flexiv 仍在 `NRT_CARTESIAN_MOTION_FORCE`。未接触时六轴全是位置控制。只有满足以下
条件才把当前探针坐标系 Z 设为力控制轴：

- 实测 Tool-Z 力与目标同号；
- 绝对值至少 2 N；
- 操作者已经按下 clutch，且模式确实是 Mode 3。

激活后调用 `SetForceControlAxis([false,false,true,false,false,false], [v,v,v])`，其中
`v=0.005 m/s` 是当前 RDK 1.9 接受的最低轴速度。力从轻触时的值在 3 秒内平滑到配置
目标，避免突然从 2 N 跳到目标。当前配置文件实际目标是 -5 N；如果实验要求 -15 N，
应在 UI 中把 `target_sensed_force_tool_z_n` 明确改为 -15，并先验证符号。

探针方向变化时，力坐标系最多以 10 Hz 更新，且角度变化达到 1°才调用一次阻塞式
`SetForceControlFrame`。每个 100 Hz 周期调用会增加 NRT 延迟，因此不能无条件更新。

接触低于 1 N 持续 50 ms 后撤销力轴，回到位置保持；一帧噪声不会触发切换。这里有
一个物理事实：同一个 Z 自由度不能同时做到“位置严格等于一个点”和“非零力严格等于
目标”。默认实现固定 X/Y 和姿态，Z 在 5 mm/s 上限内做满足接触力所需的小位移。
因此“固定点”表示不接受手柄平移、接触附近受约束，而不是数学上零位移。如果表面
移动或太软，Z 必须移动才能维持力。

### 29.3 力的测量、估计、目标与命令

项目已移除 Bota，所以不存在第二个独立传感器真值。四个力信号必须区分：

1. **实时测量**：选择 `ext_wrench_in_world`（默认）或 raw 版本的 Flexiv 世界外力，
   用实时探针旋转做 `R_probe^T F_world`，取 Z。平移参考点不影响纯力；如果比较力矩，
   才需要额外的力臂叉乘。
2. **控制估计**：对上述投影值再做 8 Hz 一阶低通，给接触门控和显示使用。它降低
   关节/状态估计纹波，但引入相位延迟。
3. **目标 sensed force**：配置希望传感器最终读到的反作用力，例如 -5 N 或 -15 N。
4. **ramped command**：真正交给 Flexiv 的力命令。未接触为 0，接触后从当前轻触值
   缓升；所以它与目标在最初几秒不同。

UI 的全宽大图同时画这四条线。白线是逐样本测量，蓝线是低通估计，绿虚线是目标，
橙虚线是缓升命令。称为“实时测量”而不是“绝对真实力”，因为它仍依赖 Flexiv 的
传感器、Elements payload 补偿和状态估计。需要力学地面真值时必须重新接独立校准
测力计并做时间同步。

## 30. 触觉反馈为什么会抖，以及当前如何稳定

机器人外力经过 bias、0.5 N 径向死区和坐标互易映射后，正常以 0.25 倍送回
omega.7。超过 15 N 后，超出部分乘 0.8 增加反作用；超过阈值 5 N 时本地速度阻尼
完全介入。最终 12 N 只是 omega.7 连续额定输出饱和，不是退出条件。

双边遥操作会形成闭环：机器人测到力 → 延迟后推动手柄 → 手柄运动又改变机器人目标
→ 新力更大。当前稳定层依次使用：

- 3 Hz 力低通，减少 Flexiv 状态估计纹波；
- 1.2 s 接入 ramp，避免 clutch 边缘力阶跃；
- 15 N/s 向量 slew limit，限制每周期力变化；
- 18 N·s/m 本地速度阻尼，直接在 omega.7 侧耗散能量；
- 时域无源观察器/能量罐。初始 0.02 J，上限 0.2 J。若命令力与手柄速度点积为正，
  表示设备正在向操作者注入能量，只允许消耗罐中已有能量；耗尽后削掉速度方向的
  主动分量。负功率会给能量罐充能。

没有使用 Kalman filter，因为主要问题是确定性的多速率时延和闭环能量注入，不是
缺少一个高斯噪声状态估计器。低通和无源控制的作用可直接测量、参数可解释；没有可靠
过程噪声/测量噪声协方差时，Kalman 只会变成难以解释的另一组滤波参数。

## 31. 重力补偿、质量矩阵和惯量的准确分工

### 31.1 默认 NRT 遥操作

Flexiv 根据 Elements 当前 active Tool 对七轴本体和“腕部处在标定零姿态时的刚性
工具”做自己的重力补偿。Python 不接管 Flexiv 七轴重力力矩，也不向七轴叠加完整
payload 重力，否则会双重补偿。

外置 q8/q9 的姿态会改变真实 CoM，但 Elements Tool 是一个固定刚体，不能表达两个
活动关节。默认配置 `dynamic_wrist_gravity_compensation=false`，所以当前默认 NRT
路径没有给 Flexiv 七轴添加 q8/q9 引起的 live-minus-zero 重力修正。Mode 3 会给
q8/q9 自己计算完整腕部重力前馈；Mode 2 主要依靠 moteus 位置内环抵抗负载。答辩时
应明确这一点：当前不是“完整九轴统一重力补偿”，而是 Flexiv 固定 Tool 补偿加外置
腕部局部补偿。

### 31.2 自定义 C++ 9DoF OSC

实验路径可以计算腕部两连杆在实时 q8/q9 和法兰姿态下的完整重力。对 q8/q9 发送
完整腕部重力；对 Flexiv 七轴只发送“实时腕部姿态重力 − q8=q9=0 时 Elements 已含
重力”的差值，避免把零姿态 payload 算两次。由于 50 Hz 腕部角度重复到 1 kHz 会
造成台阶，该模型力矩再经过 5 Hz 低通。当前默认开关关闭，是因为此前实机基线使用
Elements 补偿更稳定；启用前应先在多个法兰姿态验证符号和无负载力矩。

### 31.3 三种不同维度的“惯量矩阵”

- Elements Tool 的 **6×6 空间惯量**描述一个刚体在法兰原点的平移质量、转动惯量和
  CoM 交叉耦合。它由质量、CoM 和 3×3 CoM 转动惯量通过平行轴定理组成。
- 腕部 **2×2 关节质量矩阵** `M_w(q8,q9)` 描述两个活动关节的动能耦合，会随角度变。
- 自定义 9DoF OSC 的 **9×9 关节质量矩阵**由 Flexiv RDK 七轴 M 和两腕部刚体的
  Jacobian 投影组合而成，包含本体—腕部耦合块，不只是简单 block diagonal。
- 任务空间惯量 **6×6 Lambda** 来自 `J M^-1 J^T` 的阻尼逆，用于把期望任务加速度/
  wrench 变成动态一致的关节力矩。接近奇异点时其条件数会迅速增大。

## 32. 自定义 torque OSC 的计算过程

每个 1 kHz 周期按以下顺序运行：

1. 读取 q、dq、法兰位姿、外力、RDK 七轴 M/C/J，以及最新带时间戳 q8/q9。
2. 用串联 2R 几何计算腕部旋转、偏置探针位置和 6×2 Jacobian，拼成探针 6×9 J。
3. 用实测 q8/q9 更新两腕部刚体 Jacobian，将 6×6 body spatial inertia 投影到
   9×9 关节空间；加入辨识的反射惯量。
4. 位置误差是目标减实际；姿态误差是 `log(R_target R_actual^T)` 的最短旋转向量。
   速度误差来自目标速度减 `J dq`。
5. 任务空间使用刚度和阻尼生成期望响应，再通过动态一致 task inertia 映射为力矩。
6. 零空间投影只处理不影响主任务的冗余姿态偏好。Mode 3 使用严格位置主任务、姿态
   次任务，避免两者在固定点附近争夺同一关节。
7. 加 RDK 科氏项；根据配置决定是否加动态腕部重力差。最后做各关节绝对力矩饱和和
   力矩变化率限制，再 `StreamJointTorque`。

7DoF demo 使用已验证的较简单实现：任务增益平移 100/20、旋转 70/16、零空间 8/2、
操作阻尼 0.03，并输出 `tau_OSC + coriolis`。9DoF 因多速率腕部和额外模型耦合，稳定
难度高于 7DoF。

## 33. 为什么自定义 OSC 比 Flexiv 内置阻抗更容易不稳定

主要原因不是一个 Kp 数值，而是多个误差源共同作用：

1. **模型误差**：Elements 只标定固定刚体；两腕部的 link 分解、CoM、惯量、摩擦和
   传动柔性只能辨识近似值。OSC 使用 M^-1，模型误差会直接改变任务空间增益。
2. **多速率**：Flexiv 1 kHz，腕部常约 50 Hz。一个 q8/q9 样本被重复 20 个周期；
   速度差分和重力更新形成台阶。如果阻尼使用未滤波 dq，会产生高频力矩。
3. **USB 非实时**：fdcanusb、Linux 调度和两个控制器的顺序 query 产生变化时延。
   延迟不是白噪声，Kalman 不能自动消除。
4. **执行器内环不同**：Flexiv 接受关节力矩；moteus 稳定默认接受位置目标加前馈。
   把两者当成完全相同的理想力矩源会导致响应不一致。
5. **重复刚度**：如果 C++ 腕部 PD 和 moteus 位置 PID 同时对同一误差高增益作用，
   会变成两个弹簧叠加并在时延下振荡。当前 hybrid 模式只保留一个快速位置环。
6. **冗余和奇异点**：9 个关节完成 6D 任务有 3 个冗余方向。没有稳定零空间参考时，
   很小的末端误差也可对应很大的关节重构。接近 Jacobian 奇异点时伪逆进一步放大。
7. **目标不连续**：IK 分支、四元数符号、clutch 重捕获或掉帧速度差分都会产生一步
   目标。二阶整形、局部相对旋转和反向时清零旧方向速度用于消除这些跳变。
8. **力反馈能量**：延迟力反馈可把能量注入操作员—机器人闭环；机械臂 OSC 本身稳定
   不代表整个双边系统无源。
9. **工具标定误差**：TCP 偏移越长，同样 1° 姿态误差产生的尖端位置误差越大；错误
   CoM 同时产生随姿态变化的重力残差。

因此调试顺序必须是几何/Tool/零位 → 单轴跟踪 → 惯量质量检查 → 无触觉自由空间 →
开触觉 → 接触力，而不是直接增加 Kp。

## 34. 标定：每一种标定到底改变什么

### 34.1 Flexiv Elements Tool 标定

在物理装配变化（装/拆探针、传感器、线缆固定件）后需要重新标定并选择 active Tool。
Elements 保存质量、CoM、惯量和 TCP。质量/CoM/惯量用于 Flexiv 七轴重力和动力学；
TCP 用于把法兰命令转换成真正探针目标。`check-tool` 只读比较名称、质量、CoM、惯量、
TCP 与 TOML，绝不替代 Elements 标定。

TCP 四点法不是“四个随机姿态”。探针尖端必须始终接触同一个固定物理点，只改变
工具方向，至少记录四个差异充分的姿态。算法利用共同不动点求法兰到尖端的平移。
若尖端没有保持同一点，求出的 TCP 没有物理意义。

### 34.2 腕部应用层零位

`set-zero` 先 STOP 两个 moteus，再读取当前位置，将两个原始 output revolution 原子
写入 `zero_position_rev`，并保留 `before-zero` 备份。它不移动电机、不修改 moteus
永久编码器 offset。逻辑角度为 `sign * (raw_rev - zero_rev) * 360°`。绝对编码器跨
整圈报告时，启动会选择离当前位置最近的等价零位，避免命令几乎整圈回转。

Joint 8/ID2 行程为 ±90°；Joint 9/ID1 为 ±360°。这些是物理/线缆行程，不应为了
避免软件错误而删除。`go-zero` 才会按保存零位实际运动；`home` 使腕部回零
后，直接运动到模型计算的“Flexiv Home TCP + 世界 Z 20 cm”，不经过低位 Home 点。

### 34.3 腕部惯量辨识

`identify-inertia` 不移动 Flexiv，只读取法兰方向；q8/q9 做 120 s 平滑多正弦，默认
45°/60°。前三秒和后三秒使用 smoothstep 包络，避免阶跃。保存时间、q、dq、实测力矩、
目标 q 和世界到法兰旋转，同时保存 `assembly_id` 和零位，防止拆装后复用旧 CSV。

分析流程：dq 和力矩 8 Hz 低通；dq 数值微分后再 5 Hz 低通得到 ddq。回归同时估计
刚体尺度、两个反射惯量、两个粘性摩擦、两个 Coulomb 摩擦和两个力矩 bias。每五个
样本保留一个做验证，不参与拟合。参数使用有物理意义的 box constraints，禁止负惯量
或负摩擦通过数学方式降低残差。

PASS 条件包括：q8/q9 角度跨度至少约 8°/15°；加速度 RMS 至少 0.08/0.15 rad/s²；
拟合 RMS ≤0.35 N·m 且归一化 ≤0.65；验证 RMS ≤0.40 N·m 且归一化 ≤0.70；归一化
回归条件数 ≤500；刚体尺度不能顶到边界；在 q8/q9 全行程采样中 2×2 M 必须正定且
条件数不超过 1e5。反射惯量拟合为零不自动判 FAIL，因为它可能与刚体加速度列不可
单独辨识，只要总 M 正定且独立验证通过即可。

`check-inertia` 同时验证 active Tool，打印 6×6 空间惯量、特征值、条件数、辨识残差、
激励范围、2×2 M 最小特征值及来源。它通过只说明模型自洽且符合阈值，不等于医疗级
绝对准确；最终仍需用未参与拟合的轨迹比较预测力矩和实测力矩。

### 34.4 力零点

默认 Mode 3 使用 Flexiv 已补偿世界外力，没有额外 Bota tare。触觉反馈启动时会记录
三轴世界 bias 并在回馈前减掉；这只影响给 omega.7 的感觉，不会修改 Flexiv 内部力
控制。进行 Mode 3 前必须确认探针未受外力时 Tool-Z 读数接近零，并在多个本体姿态
复查；若偏置随姿态变化，问题通常是 Tool 质量/CoM，而不是一个常数 tare 能修复。

## 35. 多频率通信为什么这样设计

| 链路 | 协议与数据 | 频率/时序 | 设计理由 |
|---|---|---:|---|
| omega.7 | CHAI3D/DRD C++ 子进程，行式状态/力命令 | 设备环 1000 Hz | 重力补偿和触觉阻尼必须靠近设备快速运行 |
| 默认协调 | Python monotonic 定时循环 | 100 Hz | 足够更新人手目标，同时不给 USB/RDK NRT 造成过量调用 |
| Flexiv 默认 | Ethernet RDK NRT Cartesian motion/force | Python 100 Hz 发送，厂商内部更快 | 把关节伺服和重力交给厂商控制器 |
| 腕部 | fdcanusb CAN-FD，ID2/ID1 顺序 command+query | 配置 100 Hz，实际受事务时延影响 | 一个适配器不能假装两个同步硬实时力矩环 |
| 实验 OSC | C++ RDK Scheduler | 1000 Hz | RT_JOINT_TORQUE 必须固定 1 ms |
| Python/C++ | mmap 共享内存、奇偶 sequence、单调时间戳 | Python 约 50–100 Hz，C++ 1 kHz 读最新 | 无 TCP 拷贝；检测撕裂和 stale |
| UI | stdout `TELEMETRY` JSON → localhost HTTP | 20 Hz | 只观察，不阻塞控制，不做 IK/模型调用 |

腕部协议中 `P` 是两轴位置、`P8` 是仅 Joint 8 且 Joint 9 STOP、`T` 是纯前馈力矩、
`H` 是位置加前馈、`A` 启用上游 watchdog、`S` STOP。drive watchdog 1 s 必须长于
一次双电机顺序事务；上游状态 watchdog 100 ms 用于发现协调进程停止。两者职责不同。

共享内存写入先把 sequence 设奇数，写完全部字段再设偶数；读取端只有在前后 sequence
相同且为偶数时接受数据。时间戳负责 stale 判断，sequence 负责防止读半帧。

## 36. 关键配置为什么是这些数值

| 参数 | 当前值 | 选择理由与增减后果 |
|---|---:|---|

## 38. 教授可能追问的简短准确回答

**“这是 impedance 还是 admittance？”** 默认 Mode 1/2 是 Flexiv Cartesian
impedance。给定平衡位姿和刚度，外力造成位移，撤力后回平衡点。项目没有先把测得力
积分成位置命令，因此不是典型 admittance。

**“Mode 3 是完整自定义 OSC 吗？”** 默认入口不是七轴 torque OSC；它是 Flexiv
内置 Cartesian motion/force hybrid 加外置腕部任务空间控制。实验 `teleop-osc` 才是
自定义 1 kHz torque OSC。

**“Flexiv 自己做重力吗？”** 是。默认让 Flexiv 用 Elements active Tool 做七轴和
零姿态刚性工具的补偿；外置腕部自己处理 q8/q9。当前没有在默认路径对七轴加实时
q8/q9 live-minus-zero 修正，避免双算。实验 C++ 路径具备该计算但开关默认关闭。

**“为什么要 6×6 惯量？”** 6×6 描述一个刚体在三维空间的平移质量、转动惯量和
CoM 耦合。控制九个关节还需要 9×9 关节质量矩阵；做六维 TCP OSC 又需要 6×6
任务空间惯量。这三个矩阵用途不同。

**“力图的 real force 真的是绝对真值吗？”** 不是独立真值。它是 Flexiv 补偿外力
实时投影到探针 Z；estimated 是其额外低通状态。没有 Bota 时只能称 sensor-based
measurement。绝对验证需要独立校准测力计。

**“为什么不直接把控制频率都设 1 kHz？”** omega.7 和 Flexiv RT 可以 1 kHz，
但 Python、USB/CAN-FD 和两台顺序 moteus 事务不是硬实时。重复旧样本不等于新信息，
反而会把量化噪声变成力矩台阶；正确做法是时间戳、滤波、内环和 watchdog 分层。

## 39. 长 TCP 的高位 Home 目标如何直接计算

首先要区分两个概念。Flexiv 原生 `Home` primitive 是**关节空间命令**：它的
`target` 是 A1--A7 的 `JPOS`，并不是 TCP 笛卡尔目标；`tcpPoseOut` 只是动作结束后
报告的 TCP 位姿。也就是说，换成长工具不会让原生 Home 自动把工具尖端抬高。

Rizon 4(s) 默认 Home 关节位姿是 `[0,-40,0,90,0,40,0]°`。本项目只把这组关节角
当作“原始机械臂 Home 构型”的正运动学参考。程序把该向量保存为
`home.reference_joint_position_deg`，用当前机器人实时标定的 `flexivrdk.Model`
在内存中更新到这个姿态，然后读取 `Model.T("flange")`。这一步只做正运动学，
不会发送任何运动命令。

法兰位姿再右乘 Elements 当前 active Tool 的 `tcp_location`，得到低位 Home
的真实 TCP 位姿。代码只把该位姿的世界 Z 加 `home.final_lift_world_z_m=0.20`；
X、Y 和四元数全部保持 Home 值。然后使用 `Model.reachable()`，以 Home 关节角为
IK seed，检查高位目标可达并取得接近 Home 分支的七轴解。

真正运动时，腕部先回 q8=q9=0 并持续保持。Flexiv 直接进入
`NRT_CARTESIAN_MOTION_FORCE`，六个 force axis 全为 false，所以这是纯位置/姿态运动，
不是力控。IK 解被设为 `SetNullSpacePosture()` 参考，冗余姿态跟踪权重为 1.0，
而主任务始终是高位 TCP。目标以 100 Hz 发送，线速度 `0.05 m/s`、线加速度
`0.20 m/s²`。实测 TCP 在目标 `3 mm` 内连续 `0.30 s` 后才 Stop。

关键点是：代码完全不调用低位 `Home` primitive，机械臂从当前位姿直接前往
高位笛卡尔目标，因此不会先到达可能接触桌面的原始 Home 终点。但从“当前位姿”
到“高位 Home”的整个扫掠空间仍必须人工确认清空。

所以，本项目 `python3 run.py home` 的**最终受控点是当前 active Tool 的 TCP**；
原始七轴 Home 只用于定义参考 X/Y/姿态。最终七轴关节角由高位 TCP 的 IK 求得，
通常不会严格等于原始 Home 关节角。q8/q9 则单独回到并保持应用层零位。

## 40. 三个模式到底用位置、力还是力矩，以及 9DoF OSC 如何计算

### 40.1 默认 `python3 run.py teleop` 的实际控制类型

| 模式 | Flexiv 七轴 | Joint 8/9 腕部 | 上位机是否直接发关节力矩 |
|---|---|---|---|
| Mode 1，7DoF 自由空间 | `NRT_CARTESIAN_MOTION_FORCE`，六个 force axis 全关；发 TCP 位置/姿态平衡点，Flexiv 内部做笛卡尔阻抗、IK、重力和关节伺服 | Joint 8 用 moteus **位置环**回/保持零位；Joint 9 保持 STOP | 否。Python 只发 TCP pose/阻抗参数 |
| Mode 2，9DoF 自由空间 | 仍是 Flexiv 内置笛卡尔阻抗，六轴均为运动/位姿控制，不启用力轴 | Python 先做两轴几何 IK，q8/q9 通过 moteus **位置环** `P` 跟踪；Flexiv 只补腕部不能产生的姿态和偏心 TCP 平移 | 否。这是“厂商阻抗 + 外置腕部位置内环” |
| Mode 3，定点姿态+恒力 | Flexiv 的 X/Y 和 Rx/Ry/Rz 是笛卡尔阻抗位姿控制；Z 在接触门控前也是位置控制，检测到接触后才切换为 Tool-Z **力控** | 腕部外环按姿态误差计算 OSC 目标和模型前馈；moteus 用 `H` **位置环+力矩前馈** 执行 | Flexiv 不发关节力矩；腕部只发模型前馈，不是纯力矩内环 |

“Flexiv 内部最后也是电机力矩”与“本项目使用 RT 力矩接口”是两件事。
默认入口中，力矩内环完全由 Flexiv 固件管理，本项目只给它 TCP 平衡位姿、
阻抗参数和 Mode 3 力目标。

只有 `demo7`、`demo9` 和显式的 `python3 run.py teleop-osc` 才让 Flexiv 进入
`RT_JOINT_TORQUE`，C++ 以 1 kHz 向七个本体关节发力矩。`demo9/teleop-osc`
的 q8/q9 任务目标和动力学前馈也来自同一个 9DoF OSC，但默认执行仍是 moteus
混合位置+前馈，因为当前固件的纯前馈力矩实测输出过小。

### 40.2 C++ 9DoF torque-OSC 每 1 ms 做什么

1. **组成九关节状态。** `q=[q1..q7,q8,q9]`，速度同理。q1..q7 来自 RDK
   1 kHz 状态，q8/q9 来自带单调时间戳的腕部共享内存。旧样本超时时不会被当成新状态。
2. **算真正探头 TCP 的几何。** RDK 给出法兰位姿和七轴 Jacobian；两轴腕部的
   轴线、偏置和长 TCP 模型给出 2R 变换。链式求导得到探头的 `6×9` Jacobian `J`，
   前三行是线速度，后三行是角速度。
3. **构造实时 `9×9` 关节质量矩阵 `M9`。** 左上 `7×7` 基础来自 RDK。腕部每个
   刚体的 6×6 空间惯量通过该刚体的九轴 Jacobian 投影为 `J_body^T I_body J_body`，
   加到 `M9`。再加辨识的电机/减速器反射惯量。这会生成七轴与腕部之间的非零耦合块，
   不是把 `M7` 和 `M2` 简单拼成 block diagonal。
4. **计算任务误差。** 位置误差是 `p_target-p_actual`；姿态误差是
   `log(R_target R_actual^T)` 的最短三维旋转向量，不是欧拉角相减。速度误差是
   `xdot_target-J*dq`。
5. **得到期望的任务响应。** 用刚度和阻尼形成
   `a_task = Kp*pose_error + Kd*velocity_error`。它可以理解为“TCP 应该往哪个方向加速才能回到目标”。
6. **用动力学一致的任务惯量分配力矩。**
   `Lambda = inverse(J * inverse(M9) * J^T + damping^2 * I)`，然后
   `tau_task = J^T * Lambda * a_task`。`damping` 避免 Jacobian 接近奇异时逆矩阵爆大。
7. **把冗余偏好放在不影响 TCP 的空间。** 用
   `Jbar = inverse(M9)*J^T*Lambda`、`N=I-Jbar*J`，再加 `N^T*tau_posture`。
   Mode 3 不是把位置和姿态混在一个任务里，而是先解 XYZ 位置，再把姿态投影到
   位置任务的零空间，防止改姿态时拉走固定点。
8. **加模型项和力任务。** 总请求为任务力矩 + 零空间力矩 + RDK 科氏项 +
   配置允许的动态腕部重力修正。Mode 3 的接触 wrench 用 `J^T*wrench` 投影到关节。
   最后通过额定力矩和力矩变化率边界后输出。
9. **执行层仍分开。** 七个 Flexiv 关节直接收到 `StreamJointTorque`。q8/q9 在稳定
   `hybrid_position_ff` 配置中收到同一 OSC 求出的关节目标和前馈，但快速稳定环由 moteus 位置伺服完成。

因此，“九个关节共同参与任务空间计算”并不要求“九个电机都必须由同一纯力矩内环驱动”。
目标分配和动力学是耦合的，执行内环可以按硬件链路的实际能力分层。

## E1. First identify the active control path

The default command is `python3 run.py teleop`, with
`runtime.teleop_controller="flexiv_impedance"`. The robot runs Flexiv
`NRT_CARTESIAN_MOTION_FORCE`. Modes 1 and 2 use Flexiv's built-in Cartesian
impedance controller. Mode 3 stays in the same RDK session and uses Cartesian
position/orientation plus a gated Tool-Z force-controlled axis. Python does not
compute the seven Flexiv joint torques in this default path.

The custom C++ torque OSC is used by `demo7`, `demo9`, and the explicit research
command `python3 run.py teleop-osc`. Those programs switch to
`RT_JOINT_TORQUE`, run a 1 kHz Flexiv Scheduler task, and compute joint torques
from the RDK model. This distinction is essential: the default teleoperation
should not be described as a fully custom nine-joint torque OSC.

## E2. Hardware and software ownership

- **Flexiv Rizon4s:** seven arm joints, Ethernet RDK state/model access,
  Cartesian motion-force control, and an optional 1 kHz joint-torque interface.
- **External wrist:** joint 8 is moteus ID 2 and joint 9 is ID 1. Both share one
  fdcanusb CAN-FD adapter and are serviced sequentially.
- **omega.7:** six-DoF pose input, clutch switch, device gravity compensation,
  and three-axis force output through the CHAI3D/DRD bridge.
- **Pedals:** select modes only. The omega.7 clutch remains the motion enable.
- **Python coordinator:** state machine, relative mapping, wrist IK/allocation,
  default RDK commands, Mode-3 force gating, haptic feedback, and UI telemetry.
- **moteus inner loop:** fast, stable output-position tracking. In hybrid wrist
  control it tracks the OSC-generated q8/q9 target and adds model feed-forward.
- **C++ RT layer:** only the demonstrations and explicit torque-OSC backend.

## E3. Clutch-relative pose mapping

At every clutch press the software captures handle pose, physical probe pose,
arm posture, wrist angles, and flange orientation. Handle translation is first
passed through a 0.4 mm radial deadband, scaled 1:1, and mapped by the proper
right-handed transform `-x,-y,z`. Rotation uses the body-frame relative motion
`R_anchor^T R_now`. It is mapped into the probe frame and post-multiplied onto
the captured probe orientation. This prevents pitch/roll/yaw cross-coupling
when the clutch is pressed at a tilted handle pose.

The 0.25-degree angular deadband is removed continuously, so crossing the
deadband does not create a command step. Quaternion/matrix composition is used;
Euler angles are not added. Releasing and re-pressing the clutch re-centres the
human workspace without changing the robot target discontinuously.

## E4. Mode 1 — seven-DoF Flexiv Cartesian impedance

Joint 8 returns to its application zero and joint 9 remains STOP/read-only.
At the clutch edge the current seven-joint posture becomes the Flexiv null-space
reference. The controller obtains `K_x_nom` from the connected robot and applies
scales `[0.25,0.25,0.25,0.35,0.35,0.35]`; all damping ratios are 0.7.

When the clutch is released, the measured TCP becomes the equilibrium pose and
stiffness falls to `[0.04,0.04,0.04,0.08,0.08,0.08]*K_x_nom`. The robot can
therefore be pushed by hand and returns to that captured equilibrium after the
force is removed. This is impedance behavior, not classical admittance: the
application supplies an equilibrium pose and stiffness rather than integrating
measured force into a commanded position.

Python publishes Cartesian targets at 100 Hz. Flexiv's internal controller,
servo loops, gravity compensation, and safety processing run inside the robot;
100 Hz is not the motor-current-loop rate.

## E5. Mode 2 — wrist-first hierarchical nine-DoF allocation

The desired probe rotation is transformed into the clutch-time flange frame.
A damped-least-squares orientation IK uses the two wrist angular Jacobian
columns. Damping is 0.03, each iteration is limited to 4 degrees, the solver
uses at most 30 iterations, and it keeps a 2-degree joint-limit margin. A gain
of 1.0 means natural one-to-one motion; wrist angles are not amplified.

The wrist takes every orientation component available through its two physical
axes. Flexiv receives only the unreachable residual plus the requested
translation. The raw wrist target passes through a 1.5 Hz critically damped
second-order shaper, with q8/q9 speed limits of 30/40 deg/s and acceleration
limits of 120/160 deg/s^2. A moving 15-degree lead window prevents a stalled
axis from accumulating a large hidden target; it does not limit total travel.

moteus position commands use temporary `kp_scale=0.2` and `kd_scale=1.0`.
With the commissioned persistent gains this corresponds to approximately
P/D=200/30 for q8 and 240/20 for q9. Persistent PID is written only by the
explicit `apply-pid` tool.

The flange target is decoupled: the raw IK target determines which rotation the
wrist owns, while measured wrist angles determine the current offset-tip arc.
Thus the arm performs only the small translation required to keep the physical
probe point on target and does not temporarily perform wrist-reachable rotation
while the slower wrist is catching up.

## E6. Mode 3 — orientation input and Tool-Z contact force

All haptic translation is discarded. The probe XYZ captured at clutch
engagement remains the position reference; only orientation is mapped. q8/q9
again take their reachable components first, and Flexiv compensates the
offset-tip translation and residual rotation.

The wrist outer loop computes the shortest three-dimensional orientation error,
angular velocity damping, and articulated-wrist gravity feed-forward. It maps
the task moment through the angular Jacobian transpose and respects continuous
q8/q9 ratings of 6/2 N m. The stable default is hybrid control: the OSC layer
generates q8/q9 targets and model feed-forward, while the moteus position loop
provides the fast stabilizing inner loop. Pure feed-forward torque produced too
little measured motion on the commissioned firmware.

Flexiv begins with all axes position controlled. Tool-Z force control is enabled
only after measured force has the target sign and exceeds 2 N. The command then
ramps from light contact to the configured target over 3 s. Force-frame updates
are limited to 10 Hz and one-degree orientation changes because the RDK
`SetForceControlFrame` call is blocking. The Z-axis velocity is limited to
0.005 m/s. Contact below 1 N for 50 ms disables the force axis and returns to
position hold.

One degree of freedom cannot simultaneously have exact non-zero force and exact
zero displacement. X/Y and orientation remain constrained, but Z may move a
small amount to regulate contact. “Fixed point” therefore means no operator
translation and motion constrained near the captured contact, not a mathematically
zero Z displacement on a compliant or moving surface.

## E7. Mode-3 force signals and the large UI plot

There is no Bota sensor in the current runtime. The large full-width chart shows:

1. **Real-time measured:** the selected Flexiv compensated world-force source,
   projected onto the live physical probe Z axis.
2. **Controller estimate:** an additional 8 Hz first-order low-pass state of
   that projection, used by the contact logic and display.
3. **Target sensed force:** the desired sensor reaction, currently -5 N in the
   saved profile; use -15 N only after sign validation.
4. **Ramped command:** the value actually sent after contact gating and ramping.

“Measured” is not independent ground truth. It depends on Flexiv sensing,
Elements payload compensation, and state estimation. An independently calibrated
and synchronized load cell is required to claim absolute force ground truth.

## E8. Haptic feedback and passivity

The Flexiv force is bias-corrected, passed through a 0.5 N radial deadband, and
mapped reciprocally into the device frame. Nominal feedback gain is 0.25. Above
15 N, excess force receives an additional gain of 0.8 and activates up to
20 N s/m overload damping. The omega.7 output saturates at its 12 N continuous
rating; saturation never terminates teleoperation.

The delayed bilateral path is stabilized with a 3 Hz low-pass filter, a 1.2 s
engagement ramp, a 15 N/s vector slew limit, 18 N s/m local damping, and a
time-domain passivity energy tank. The tank starts at 0.02 J and is capped at
0.2 J. Positive device power consumes stored energy; when insufficient energy
remains, only the force component along device velocity that would inject
energy is reduced. Dissipative power replenishes the tank.

A Kalman filter is not used because the dominant problem is deterministic
multi-rate delay and energy injection, not state estimation under a validated
Gaussian process/noise model. Low-pass filtering plus passivity has an explicit,
measurable role and fewer unidentifiable assumptions.

## E9. Gravity compensation and dynamic models

In default NRT teleoperation, Flexiv performs arm gravity compensation using the
active Elements Tool, which represents the complete assembly as a rigid body at
the calibrated zero wrist pose. Python does not add a second full payload gravity
term to the seven arm joints. The external wrist controller computes q8/q9
gravity feed-forward in Mode 3; Mode 2 relies mainly on the moteus position loop.

Because the Elements Tool is rigid, it cannot represent changing q8/q9 geometry.
The default `dynamic_wrist_gravity_compensation=false` means there is currently
no live q8/q9-minus-zero gravity correction added to the seven Flexiv joints in
the NRT path. The experimental C++ model can compute full live wrist gravity for
q8/q9 and only the live-minus-zero delta for the arm, thereby avoiding double
counting the Elements zero-pose payload. This option is kept off until its sign
and magnitude are validated over several flange attitudes.

Three different inertia matrices are used. The Elements **6x6 spatial inertia**
describes one rigid tool at the flange. The articulated wrist has a dynamic
**2x2 joint mass matrix**. Custom nine-DoF OSC builds a coupled **9x9 joint mass
matrix** and derives a **6x6 task-space inertia Lambda** for the probe task.
These matrices are related but not interchangeable.

## E10. Custom torque OSC details

At 1 kHz the C++ controller reads arm state/model data and the newest timestamped
wrist state; evaluates the 2R wrist kinematics, the 6x9 probe Jacobian, body
Jacobians, and coupled mass matrix; computes position error and logarithmic
rotation error; forms stiffness/damping task response; maps it through a damped
dynamically consistent task inertia; adds null-space posture torque and RDK
Coriolis; optionally adds dynamic wrist gravity; and finally applies physical
joint-torque and torque-rate limits before `StreamJointTorque`.

Mode 3 in the experimental backend is hierarchical: XYZ position is the primary
task, residual arm orientation is projected underneath it, and force is enabled
only near the captured point. This prevents force regulation or orientation from
overriding recovery of a displaced contact point.

## E11. Why the custom OSC can be less stable

The major causes are model mismatch, a 1 kHz arm versus 50–100 Hz non-real-time
wrist link, variable USB scheduling delay, different arm and wrist actuator inner
loops, duplicated PD stiffness, redundant inverse solutions, Jacobian
singularities, target/IK branch discontinuities, long TCP offsets, and delayed
bilateral force energy. Increasing Kp does not fix these causes and often makes
them worse. The intended debugging order is geometry/Tool/zero calibration,
single-axis tracking, inertia validation, free-space motion without feedback,
feedback in free space, and finally contact-force tests.

## E12. Calibration details

Elements calibration must be repeated whenever the physical assembly changes.
It supplies mass, centre of mass, rotational inertia, and TCP. For a TCP pivot
calibration the tip must touch one fixed physical point in at least four diverse
orientations; four random free-space poses are invalid. `check-tool` only verifies
the live result against the saved profile.

`set-zero` sends STOP, reads both output positions, and atomically saves them as
the application zero with a backup. It does not move a motor or change persistent
encoder firmware. q8 is limited to +/-90 degrees and q9 to +/-360 degrees around
that zero. `go-zero` performs motion; `home` zeros the wrist and moves directly
to the modeled Flexiv Home TCP plus 0.20 m world Z without visiting low Home.

Wrist inertia identification runs a 120 s smooth multi-sine q8/q9 excitation,
normally 45/60 degrees. It records q, dq, measured torque, target q, flange
orientation, assembly ID, and zero. Analysis filters dq and torque at 8 Hz,
differentiates/filters acceleration at 5 Hz, and fits rigid-body scale, two
reflected inertias, viscous and Coulomb friction, and torque biases using bounded
least squares. One fifth of samples are held out for validation.

PASS requires sufficient q and acceleration excitation, fit RMS <=0.35 N m,
validation RMS <=0.40 N m, normalized residual limits, regression condition
number <=500, no rigid-body-scale bound hit, and a positive-definite 2x2 mass
matrix across the configured joint range. A PASS is a model-consistency check,
not metrological certification.

## E13. Multi-rate communication

The omega.7 device loop runs at 1 kHz. Default Python coordination and Cartesian
publishing run at 100 Hz. The wrist bridge is configured for 100 Hz but actual
rate depends on sequential ID2/ID1 USB/CAN transactions. Experimental wrist
state publication is commonly 50 Hz while C++ consumes the latest sample at
1 kHz. Shared memory uses odd/even sequence numbers to reject torn frames and
monotonic timestamps to reject stale frames. The UI receives separate structured
JSON telemetry at 20 Hz and never performs IK or dynamics calls.

The moteus protocol uses `P` for two-axis position, `P8` for q8 with q9 stopped,
`T` for feed-forward torque, `H` for position plus feed-forward, `A` to arm the
upstream watchdog, and `S` for STOP. The 1 s drive watchdog covers complete
sequential bus transactions; the 100 ms upstream watchdog detects a dead
coordinator. They protect different failure layers.

## E14. How to interpret the 14 UI charts

The UI contains one large Mode-3 force chart, four probe-TCP charts, and nine
individual joint-error charts. The position and orientation task errors use the
physical probe after live wrist geometry. Orientation error is the shortest
rotation from actual to target, not subtraction of Euler angles.

J8/J9 target is the commanded moteus position. Flexiv's NRT Cartesian interface
does not expose its internal instantaneous joint trajectory, so J1–J7 target is
the null-space posture reference supplied by this project. J1–J7 error therefore
measures posture-reference deviation, not an inaccessible internal joint-servo
following error. The TCP error plots are the primary measure of teleoperation
accuracy.

## E15. Direct elevated Home target for a long TCP

Flexiv's native `Home` primitive is a **joint-space command**: its `target` is
the A1--A7 `JPOS`, not a Cartesian TCP target. `tcpPoseOut` only reports the
resulting TCP pose after the motion. Attaching a long tool therefore does not
make native Home automatically raise or protect the tool tip.

The documented Rizon 4(s) default Home joint posture is
`[0,-40,0,90,0,40,0] deg`. The program stores it as
`home.reference_joint_position_deg`, updates the live calibrated
`flexivrdk.Model` to that configuration in memory, and reads
`Model.T("flange")`. This is forward kinematics only and sends no motion.

The flange transform is composed with the active Elements Tool TCP. The code
adds `home.final_lift_world_z_m=0.20` only to world Z, keeping Home X/Y and the
quaternion unchanged. `Model.reachable()` uses the Home joints as its IK seed
to verify reachability and select the nearby seven-axis branch.

During real motion q8/q9 first return to and hold zero. Flexiv enters
`NRT_CARTESIAN_MOTION_FORCE` with all force axes disabled, so this is pure
pose control rather than force control. The IK solution becomes the null-space
posture reference while the primary task is the elevated TCP. The target is
sent at 100 Hz with 0.05 m/s velocity and 0.20 m/s2 acceleration, and Stop is
issued after measured TCP error remains below 3 mm for 0.30 s.

Most importantly, the code never executes the low official Home primitive; it
moves directly from the current pose to elevated Home. The complete swept volume
between those two poses must still be verified clear.

Therefore, the final controlled point of `python3 run.py home` is the current
active Tool TCP. The native seven-axis Home configuration supplies only the
reference X/Y/orientation. IK computes the final seven-axis joints, which will
normally differ from the native Home joints, while q8/q9 return to their
application-level zeros.
